# G6 — Rigid body point cache

Points: 5. Epic G. Depends on [G4](g4.md) and [G5](g5.md).

Blender spec: `BKE_pointcache.h`, `BKE_ptcache_id_from_rigidbody`, the read-or-step branch in `BKE_rigidbody_do_simulation`.

## What to do

Store each rigid body's transform per simulation frame on disk or in a folder next to the scene. If the cache has the frame, copy it and do not step. Playback backward reads the cache. A change to gravity, a shape, a mass, or a constraint marks the cache outdated from that frame forward. The first play fills the hole one frame at a time.

## How to do

1. Cache folder: `<scene>_physics/rigid/frame_00001.bin` or one file with a frame index. Each record is body id, position, quaternion, linear velocity, angular velocity.
2. On evaluate while playing:
   - Exact hit: read records, write evaluated transforms, set `last_time`, return.
   - `time == last_time + frame_dt`: run [G5](g5.md), then write the frame.
   - Any other time: do not simulate. Status line "outdated cache" or "no cache for this frame".
3. Outdated: changing a world field or any `RigidBodySettings` or a constraint on a body sets `outdated_from` to the current frame. Frames at or after that index are deleted. Frames before it stay.
4. A Bake button on the Physics tab runs the forward loop from the current frame to `duration` with the display cap disabled for that button only, because the user asked for a bake. It still writes one frame at a time and can be cancelled. Esc cancels. The partial bake stays.
5. Muted world reads the cache and does not write.

## What to consider

- This is not the OpenVDB cache. Do not put grids in this folder. [H3](../epich/h3.md) has its own directory.
- Velocities are in the cache so a resume from a mid frame does not explode. Transforms alone are not enough.
- Body ids are the object ids. A deleted object leaves stale records. Ignore records whose id is gone. A new body at an old frame is a cache miss for that id and dirties from the frame it appears.
- Do not read the cache on the draw thread while bake writes it, until you have a second thread. Bake runs on the main thread and pumps the window, or it blocks with a progress fraction. Blocking with progress is acceptable. A data race is not.

## Output

Play from the start writes frames. Scrubbing back shows the fall without stepping. Changing gravity clears frames from now forward and the status line says the cache is outdated. A second play refills them. Bake fills to the end and the next scrub does not move the solver.
