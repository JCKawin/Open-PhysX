# B5 — FBX, Alembic, and USD are later

Points: 3. Epic B. Depends on [B4](b4.md). This story is a written boundary, not an importer.

Blender spec: `io/fbx`, `io/alembic`, `io/usd`.

## What to do

Do not build FBX, Alembic, or USD in the first physics path. Write down what each format is for, which Blender files are the spec when the work starts, and what must already exist. The File menu does not show disabled items that look half-built. Either omit them or show them labeled "Later" with no click handler.

## How to do

1. Add a short section to this file's sibling only if a menu string is required. The decision itself is this document.
2. When the work starts, after Epic G and Epic H caches round-trip, the order is:
   - FBX mesh and transform only (`io/fbx/importer/fbx_import_mesh.cc`). Armatures stay out until constraint story [F4](../epicf/f4.md) is reopened.
   - Alembic mesh and transform cache (`io/alembic`). This is a playback cache of topology, not the rigid-body point cache.
   - USD mesh and xform (`io/usd`). Materials, lights, and Hydra stay out.
3. Each future importer uses the axis and unit boundary from [B3](b3.md). USD and FBX both carry an up-axis. Read it. Do not assume Z-up.
4. One object per mesh primitive, same as OBJ, until the scene graph importer exists.

## What to consider

- These libraries are large builds. Adding them before a mesh round-trip and a scene file is how the physics work stalls.
- Alembic time samples are not a substitute for [G6](../epicg/g6.md). Do not store rigid-body frames in Alembic in the first cache.
- GPL and third-party licenses of the FBX SDK versus a clean parser matter. Blender's current FBX importer is its own parser. Follow that. Do not take the Autodesk SDK as a dependency without a separate decision.

## Output

The menu does not promise FBX, Alembic, or USD. A reader of this file knows the order and the Blender files to open when that work starts. OBJ, STL, and PLY remain the importers that ship with the physics path.
